---
name: Supabase direct DB access from Replit
description: How to get a working Postgres connection to this project's Supabase DB for running migrations, the network pitfall that blocks the naive approach, and how to verify you're pointed at the right project.
---

- This project ships with only the Supabase anon/publishable key in env — no service-role key, no DB URL, no Supabase CLI login. PostgREST cannot run arbitrary DDL, so applying migrations requires a direct Postgres connection string from the user (Supabase dashboard → Project Settings → Database → Connection string).
- **Pitfall 1 — IPv6:** the "Direct connection" host (`db.<ref>.supabase.co:5432`) resolves to an IPv6-only address; this environment has no IPv6 egress, so `psql` fails with an opaque, empty `psql: error:` message. Use the **Session pooler** connection string instead (host contains `pooler.supabase.com`, username `postgres.<project_ref>`) — it has an IPv4 address.
- **Pitfall 2 — project mismatches are common and silent.** A DB connection string, an anon/publishable API key, and the app's configured `SUPABASE_URL`/`SUPABASE_PROJECT_ID` can each reference a *different* Supabase project without any obvious error — `psql` will happily connect and even show tables if the wrong-but-still-valid credentials belong to some other unrelated project. **Always cross-check the project ref** embedded in the DB host/username against the project ref in the URL and against a live REST call with the given anon key before trusting that all three point to the same project:
  - `curl https://<ref>.supabase.co/rest/v1/<known_table>?limit=1 -H "apikey: <key>"` — a `PGRST205`/table-not-found means the key is valid for that project but schema differs; `"Invalid API key ... might be owned by another project"` means the key belongs elsewhere entirely.
  - Before running any destructive schema operation (`DROP SCHEMA ... CASCADE`), list existing tables first (`select tablename from pg_tables where schemaname='public'`) and confirm with the user if they don't match what's expected — do not assume "empty-looking" or "wrong" means safe to wipe.
- Once the correct pooler URL is confirmed, apply this project's `supabase/migrations/*.sql` files in filename order via `psql "$URL" -v ON_ERROR_STOP=1 -f <file>` — they are idempotent-safe individually but assume prior files already ran (enums/helper functions from earlier files are reused).
- Storage buckets (`school-assets`, `staff-assets`, `student-assets`) are **not** created by any migration file — they must be inserted manually (`insert into storage.buckets (id, name, public) values (...)`) after schema migration; their RLS policies *are* included in the migrations.
- The `delete-account` Supabase Edge Function (`supabase/functions/delete-account`) is not deployed by DB migrations — it requires `supabase functions deploy` with a Supabase access token (management API), which is a separate credential from the DB connection string.
