# Edvimia — AI School Operating System

A TanStack Start (React + TypeScript) web application — an AI-powered operating system for primary and secondary schools. Built with Lovable and imported to Replit for continued development.

## Stack

- **Framework**: TanStack Start (SSR) + TanStack Router (file-based routing)
- **Auth & Database**: Supabase
- **UI**: Tailwind CSS v4 + shadcn/ui (Radix UI)
- **Package manager**: Bun
- **Build tool**: Vite (via `@lovable.dev/vite-tanstack-config`)

## Running the app

```bash
bun run dev   # starts dev server on port 5000
```

The workflow "Start application" is configured to run `bun run dev` automatically.

## Environment variables

Set in Replit's shared environment (sourced from `.env`):

| Key | Description |
|-----|-------------|
| `VITE_SUPABASE_URL` | Supabase project URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Supabase anon/publishable key |
| `SUPABASE_PROJECT_ID` | Supabase project ID |

## Project structure

```
src/
  routes/         # File-based routes (TanStack Router)
    __root.tsx    # App shell — wraps every page
    index.tsx     # Root redirect (auth-aware)
    welcome.tsx   # Landing page
    login.tsx / signup.tsx / ...
    _authenticated/  # Protected routes
  components/     # Shared UI components (shadcn/ui)
  lib/            # Auth, utilities
  integrations/   # Supabase client & types
supabase/
  migrations/     # Database migrations
```

## Supabase migration (July 14, 2026)

Edvimia was disconnected from the original Lovable-managed Supabase project and migrated to a user-owned project (`wbqdlgzdzauqsbqijwxf`). What was done:
- Replayed all `supabase/migrations/*.sql` files (in order) against the new project — 45 tables, 15 enums, 20 functions, all RLS policies, and the `on_auth_user_created` trigger were recreated identically. No data was migrated (clean production DB, per request).
- Created the 3 storage buckets used by the app (`school-assets`, `staff-assets`, `student-assets`, all private) — these are not created by any migration file, only their RLS policies are.
- Updated env vars (`SUPABASE_URL`, `VITE_SUPABASE_URL`, `SUPABASE_PROJECT_ID`, `VITE_SUPABASE_PROJECT_ID`, `SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PUBLISHABLE_KEY`) and `supabase/config.toml` to point at the new project.
- Verified via a real signup: `handle_new_user` trigger fires and creates a `profiles` row correctly on the new project. Test user was deleted after verification.
- **Not yet done / manual follow-up needed:** the `delete-account` Edge Function (`supabase/functions/delete-account`) was not redeployed — that requires `supabase functions deploy` with a Supabase access token (a different credential from the DB connection string), which wasn't requested in this session. Until redeployed, the "delete account" feature in Settings will fail against the new project.
- The new project has "Confirm email" enabled by default (standard Supabase default) — users must click an email confirmation link before they can log in. This is a Supabase auth setting, not app code, and can be changed in the dashboard under Authentication → Settings if not wanted.
